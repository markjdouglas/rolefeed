One collection lost to a failed push Monitoring Minor

Occurred 07/10/2026, 16:53 UTC Collections lost 1 Feed stale 4h 04m Cause this repository Data loss none Run 37655430555

The collection worked and the commit of it did not. Run 196 set up its runner, installed its dependencies, queried all 62 employers and wrote 967 roles to disk — then failed at the step that commits the result, and the whole run was marked failed. The data existed for about a second and was thrown away with the runner.

This is not the same failure as 5 October, although the email in your inbox looks identical. That one never got a runner and ran zero steps, and the cause sat inside GitHub. This one ran every step and the cause is here.

Updates — newest first, all times UTC

  • 19:55Fix shipped in v0.4.6. The commit step now retries the push three times with a widening pause, reconciling against the remote between attempts. One further scheduled collection is needed before this closes.
  • 18:56Recovered unaided. The next scheduled collection completed normally, which is the expected behaviour: the fault was in the delivery of one run's output, not in the pipeline, so nothing was left broken to repair. The feed was 4h 04m behind at its worst.
  • 17:10Identified. Step-level results place the failure precisely: Collect roles passed and Summarise the run passed, reading the same two fields from the same file that the commit step reads. That clears the collector and the JSON, leaving the push as the only thing in the step that can fail. The twelve annotations say nothing more specific than "process completed with exit code 1", and GitHub's run logs need credentials this session does not hold — so this is reasoned from which steps passed, not read off a log.
  • 16:53Run 196 failed after 1m 12s at Commit the feed if it changed. Every other step succeeded. Notification sent.

Root cause

The commit step ran git push once, with nothing after it. A push is a single network call to a service with no uptime guarantee, placed at the very end of a job whose expensive work is already finished and held only in the runner's filesystem. The cheapest step in the pipeline was the one with no tolerance for failure, and when it failed it discarded the output of the expensive ones.

Remediation

The push now retries three times, pausing ten then twenty seconds. Between attempts it reconciles with the remote by last-write-wins rather than by rebasing: the generated file is set aside, the branch is reset onto whatever the remote now holds, the file is put back and committed again. That is sound here specifically because jobs.json is generated and has exactly one writer, so a newer collection is always the correct answer and there is no merge to get wrong — and because a rebase conflict in an unattended job leaves the repository stopped half way through a rebase, in a file nobody edits by hand.

The threshold set on 5 October — three cancelled runs in a fortnight before building retry machinery — was about runner allocation, a fault with a cause outside this repository and a habit of curing itself. It does not cover this. A push that drops a completed collection is a local fault with a three-line fix, and the argument against defending a transient third-party outage is not an argument against retrying your own network call.

Resolution criteria

Two consecutive scheduled collections completing after the fix is live. The run at 18:56 recovered on its own and is not counted: it ran against the old step, so it says nothing about whether the retry works. The same rule as last time, for the same reason.

Scheduled collections did not run Resolved Minor

Started 05/10/2026, 18:55 UTC Resolved 06/10/2026, 00:56 UTC Feed stale 5h 55m Cause upstream — GitHub Actions Data loss none

GitHub stopped allocating runners to this repository's jobs. Each job queued for about fifteen minutes and was then cancelled without executing a single step, under an incident GitHub acknowledged on its own status page. The feed went 5h 55m between successful collections, from 16:53 to 22:48 UTC, and stated its own age on the front page throughout. The cost was currency, not correctness.

Updates — newest first, all times UTC

  • 00:56Resolved. A second consecutive scheduled collection completed, meeting the criterion set when this entry was opened. Every collection since has also completed.
  • 22:48Collection succeeded — 970 roles, the first since 16:53. GitHub had begun assigning runners again. One success was deliberately not treated as resolution.
  • 20:15Identified as upstream. GitHub's status page shows an open incident: delays assigning GitHub-hosted runners, affecting workflow start times across multiple runner configurations, under investigation since 19:11. That is the same minute the first run here was cancelled, so this project hit the leading edge of the incident rather than a known one. Nothing to fix on this side.
  • 20:02Recovery attempt failed. Run 37365567052 was cancelled after 15m 05s with the same annotation, having run on ubuntu-24.04 rather than ubuntu-latest. Two different runner labels, one identical failure mode, which rules out the runner pin made earlier as a cause.
  • 19:35Correction. This entry previously recorded the incident as resolved at 19:35, on the grounds that a manual collection had been dispatched. That was wrong on its own terms: the dispatched run had not yet finished when the claim was written, and it went on to fail. A recovery action is not a recovery.
  • 19:30Investigated. The Actions API showed zero steps executed and the annotation "The job was not acquired by Runner of type hosted even after multiple attempts", which excludes any application fault.
  • 19:11First failure. Scheduled run 37359683002 cancelled after 15m 03s without ever being assigned a runner. Failure notification sent.
  • 18:55Scheduled run queued as normal. Last successful collection was 16:51.

Root cause

GitHub Actions accepts the job, puts it in the queue, and then fails to assign it a hosted runner. After roughly fifteen minutes its scheduler gives up and cancels the job. This is a capacity or allocation failure inside GitHub's own infrastructure, now acknowledged by GitHub as an open incident.

Four things put that beyond reasonable doubt. The jobs executed zero steps, so nothing written here ran at all. The seventeen preceding runs succeeded on identical code in about a minute each. The commit at the head of the first failed run was one of the collector's own data commits, so no code had changed. And the two failures used different runner images, which eliminates the only local variable between them.

Why nothing needs repairing

Every collection is a full refresh rather than an increment. Each run re-queries all 62 reachable employers and rebuilds the feed from scratch, with the state merge preserving each role's first-seen date across runs. A missed run therefore costs currency, never correctness, and the next successful run restores everything without intervention. A pipeline built on deltas would need a repair job here.

Remediation

No fix has been applied to the failure itself and none is planned while the cause sits upstream. Adding retry machinery to defend against a third-party capacity fault would mean building permanent complexity in response to a temporary problem, and every piece of added machinery is a new thing that can fail. Waiting is the correct action, not the lazy one.

That judgement is falsifiable, so here is the threshold: three cancelled runs in a fortnight would make this a pattern rather than an incident, and would justify a scheduled retry a few minutes after a cancellation. Two failures inside one acknowledged provider incident do not meet it.

One unrelated change was made during the investigation and should not be mistaken for a fix. The first failed run carried three notices warning that the ubuntu-latest label migrates to Ubuntu 26 from 19 October 2026, so the image was pinned to ubuntu-24.04. That converts an operating system change arriving on someone else's schedule into a deliberate upgrade with a diff and a test run. The second failure then happened on the pinned image, which is how the pin was cleared of involvement.

Resolution criteria, and whether they worked

This entry moved to resolved when two consecutive scheduled collections succeeded — not when the first one did, and not when GitHub closed its own incident. One green run after a capacity fault is weak evidence; two is enough to say the schedule is working again. Writing that rule down while the incident was still open is what made the closing decision a check rather than a judgement.

What this exposed

The dated runner warning had been attached to every previous successful run as well, and nobody reads annotations on a green build. It took an unrelated failure to surface it. Warnings on passing runs are effectively invisible, which generalises well beyond this project.

The second lesson is about this page. Its first version declared the incident resolved fifteen minutes before the evidence supported it, because dispatching a fix felt like fixing it. A status page is only useful if it is allowed to say "still broken", which means resolution has to be defined in advance and checked against the record rather than against intent.

The third is about estimating from inside an outage. That same first version put the cost at "roughly two extra hours" of stale data while the incident was still running. The gap between successful collections was 5h 55m — nearly three times the estimate. The error was not in the arithmetic but in the assumption underneath it, that a capacity fault resolves on the timescale of the one cancelled run you have seen so far. Duration is the one field a live incident log should leave empty until it can be measured.
